## 2. Результаты этапов 0–5

#### Этап 0: стресс-тест
`java -cp out lab2.Stress 10000 <window> <version>`, число овердрафтов из 10 000 прогонов:

| Версия, `window` | Прогон 1 | Прогон 2 | Прогон 3 |
|---|---|---|---|
| V1, `none` | 2 | 7 | 3 |
| V1, `yield` | 151 | 157 | 152 |
| V2, `none` | 0 | 0 | 0 |

Числа разные, потому что порядок потоков выбирает планировщик ОС, а он зависит от загрузки ядер, прерываний и момента пробуждения потоков после барьера; код при этом один и тот же. Ноль овердрафтов у V1 ничего не доказал бы: значит только, что за эти прогоны плохое чередование не выпало, а баг в коде остаётся.

#### Этап 3: Random
| Программа | seed'ов | Ошибок (%) | Первая ошибочная трасса | Повтор |
|---|---|---|---|---|
| `withdraw-v1` | 1000 | 501 (50,1%) | seed 0: `BBAABBAA` | 10/10 |

Лог `withdraw-v1 replay BBAABBAA log`:
```
  B  lock mu        \
  B  unlock mu       | B проверил: balance = 100 >= 100, ok = true
  B  window         /
  A  lock mu        \
  A  unlock mu       | A вклинился между проверкой и списанием B: balance всё ещё 100, ok = true
  A  window         /
  B  lock mu        \  B списал: balance = 0
  B  unlock mu      /
  A  lock mu        \  A списал по устаревшей проверке: balance = -100
  A  unlock mu      /
schedule BBAABBAA -> OVERDRAFT balance=-100 results=true,true
```
Поток A выполнил свою проверку в окне `window()` потока B, то есть между проверкой и списанием B. Оба увидели 100, оба списали по 100, итог −100.

Трасса лучше, чем «запустить ещё 1000 раз», потому что она воспроизводит баг детерминированно (10/10): по ней можно пройти шаги с логом, отладить исправление и оставить как регрессионный тест. Повторный стресс-тест может больше ни разу не попасть в это чередование.

#### Этап 4: DFS
| Программа | Расписаний | Ошибок | Первая ошибочная трасса | Почему программа на ней ломается |
|---|---|---|---|---|
| `withdraw-v1` | 6 | 4 | `AABBAABB` | A и B оба проверили баланс (100) до того, как кто-то списал; затем оба списали: −100 |
| `withdraw-v2` | 2 | 0 | — | проверка и списание в одной критической секции, вклиниться некуда |
| `withdraw-v0` | 20 | 18 | `AABABB` | лока нет: B прочитал 100 до записи A, потом прочитал 0 после неё и записал −100 |
| `transfer` | 6 | 2 | `AB` | A держит `a` и ждёт `b`, B держит `b` и ждёт `a`: deadlock |

Лог `withdraw-v1 replay AABBAABB log`: A проверил (`lock/unlock mu`, ok = true), `window`; B проверил (ok = true, баланс ещё 100), `window`; A списал (0); B списал (−100). Тот же баг, что на этапе 3, только вклинился B, а не A.

Лог `withdraw-v0 replay AABABB log`:
```
  A  balance -> 100     A: проверка, ok = true
  A  window
  A  balance -> 100     A: прочитал для списания
  B  balance -> 100     B: проверка, ok = true (A ещё не записал)
  B  window
  A  balance = 0        A: записал 100 - 100
  B  balance -> 0       B: прочитал для списания
  B  balance = -100     B: записал 0 - 100
```
Без лока B успел проверить баланс между чтением и записью A.

Лог `transfer replay AB log`: `A lock a`, `A window`, `B lock b`, `B window`, затем оба ждут занятый лок, `enabled` пуст: `DEADLOCK held={a:A, b:B}`.

У `withdraw-v2` расписаний меньше, потому что весь `withdraw` идёт под одним локом. Пока A держит `mu`, B ждёт лок и не попадает в `enabled`, поэтому на всех паузах внутри секции выбор единственный. Развилка одна: кто первым возьмёт лок, отсюда 2 расписания. В `withdraw-v1` лок отпускается между проверкой и списанием, и на этих паузах второй поток может вклиниться.

## 3. Результаты этапа 6 (Коллектор)

| Программа | Расписаний | Ошибок | Первая ошибочная трасса | Почему DFS видит / не видит баг |
|---|---|---|---|---|
| `collector-nostep3-1x1` | 106 | 12 | `ABBBAABAAB` | видит: между чтением `active` и записью `inside` есть пауза, и читатель успевает в ней переключить буфер |
| `collector-plain-1x1` | 29 | 0 | — | не видит: `inside` — обычное поле, паузы между чтением `active` и записью `inside` нет, и опасное окно для планировщика не существует |
| `collector-acqrel-1x1` | 636 | 0 | — | не видит: баг в переупорядочивании записи и чтения процессором, а планировщик перебирает только порядок шагов (как при seq_cst) |
| `collector-ok-1x1` | 636 | 0 | — | ошибки нет на самом деле: шаг 3 закрывает окно, seq_cst не даёт переупорядочиваний |

Лог `collector-nostep3-1x1 replay ABBBAABAAB log` (A — писатель, B — читатель):
```
  A  active -> 0        писатель выбрал буфер b = 0, но ещё не объявил inside
  B  active -> 0        читатель: old = 0
  B  active = 1         читатель переключил active на буфер 1
  B  await done         inside[W1] = -1 != 0: читатель решил, что в буфере 0 никого нет
  A  inside[W1] = 0     писатель объявил, что пишет в буфер 0 (уже поздно; шага 3 нет)
  A  cnt[W1][0] -> 0    писатель читает счётчик буфера 0
  B  cnt[W1][0] -> 0    читатель забирает буфер 0: global += 0
  A  cnt[W1][0] = 1     писатель записал запись в буфер 0
  A  inside[W1] = -1
  B  cnt[W1][0] = 0     читатель обнуляет буфер 0 и стирает запись писателя
schedule ABBBAABAAB -> LOST 1 record(s): counted 0 of 1
```
Читатель посчитал буфер 0 пустым на `await done`: писатель уже прочитал `active = 0`, но ещё не записал `inside = 0`. Писатель положил данные в старый буфер 0, хотя `active` уже 1. Читатель прочитал счётчик до записи писателя и после неё обнулил его, поэтому запись потерялась. Шаг 3 (повторная проверка `active == b`) заметил бы переключение и отправил писателя в буфер 1.

Ответы на вопросы:
- "Почему одного писателя с одним вызовом `record()` оказалось достаточно, чтобы найти баг в алгоритме": Потому что баг заключается в гонке одного вызова `record()` с одним `snapshot()`: окно между чтением `active` и записью `inside`. Второй писатель или второй вызов только добавляют расписаний.
- "Почему `collector-plain-1x1` даёт 0 ошибок при наличии бага в коде": Потому что `inside` — обычное поле. Перед его записью нет паузы, чтение `active` и запись `inside` для планировщика идут одним шагом, и вклиниться между ними нельзя. Баг есть, но планировщик его не видит.
- "В чём разница между нулём ошибок у `collector-acqrel-1x1` и нулём ошибок у `collector-ok-1x1`": Ноль у `collector-acqrel-1x1` — ложный: баг есть, но он появляется только из-за переупорядочивания записи и чтения процессором, которое планировщик не моделирует. Ноль у `collector-ok-1x1` настоящий: ни одно чередование шагов не ломает код, а seq_cst запрещает такие переупорядочивания и на железе.

## 4. Результаты этапа 7 (Store Buffering)

`java -cp out lab2.MiniStress <mode> 2000 10000`, `naive 200000 1` — 3 прогона:

| Режим | (0, 0) есть? | Пояснение |
|---|---|---|
| `plain` | да (9 051 из 2·10⁷) | обычные поля: и процессор (store buffer), и JIT могут поставить чтение раньше записи |
| `acqrel` | да (1 217 из 2·10⁷) | release/acquire не запрещает ставить чтение другой переменной раньше своей записи, а store buffer на x86 так и делает |
| `volatile` | нет (0 из 2·10⁷) | seq_cst: JVM ставит барьер между записью и чтением, store buffer сбрасывается до чтения |
| `naive` | нет, 0 из 3 | барьер вокруг каждой пары: потоки почти никогда не исполняют одну пару одновременно |

#### Размер пачки (задание 7.1)
| Команда | (0, 0), % |
|---|---|
| `acqrel 200000 100` | 0,00016% (31 из 2·10⁷) |
| `acqrel 200 100000` | 0,0066% (1 312 из 2·10⁷) |

Объяснение по коду: исход (0, 0) в ячейке `i` получается, только если оба потока обрабатывают одну и ту же ячейку почти в одну наносекунду, пока записи друг друга ещё сидят в store buffer. После барьера `go` потоки просыпаются с разбросом в микросекунды. Пачку из 100 ячеек первый поток проходит быстрее этого разброса, и второй начинает, когда первый уже закончил. С пачкой в 100 000 ячеек проход длится дольше разброса, проходы потоков пересекаются во времени, и отстающий поток может догнать лидера на тех же индексах.

Ответы на вопросы:
- "Почему исход `(0, 0)` появляется в режиме `acqrel`, хотя на этапе 6 DFS показал 0 ошибок на `collector-acqrel-1x1`": Потому что DFS перебирает только порядок шагов потоков, считая каждый шаг мгновенно видимым всем (seq_cst). Переупорядочивание записи и последующего чтения процессором (store buffer) лежит вне его модели: такого расписания в дереве просто нет.
- "Сравните `naive` с пачечным режимом на своей машине. Что это говорит о том, насколько результат зависит от устройства стенда": На моей машине `naive` не дал (0, 0) ни в одном из 3 прогонов, а пачечный режим дал. Один и тот же тест в зависимости от способа запуска потоков то ловит эффект, то нет. Значит, результат сильно зависит от стенда и устройства теста, и отсутствие (0, 0) в одном прогоне не доказывает корректность.
